01 — The problem

A simple booking can become a database problem.

A hotel website serves many users at once. Trouble begins when two transactions check the same room and dates before either one has written its booking.

At the same moment, Aarav and Meera open the hotel website and see Room 205 as available for the same dates.

AaravChecks 10–12 Oct → free
↓
Creates booking
MeeraChecks 10–12 Oct → free
↓
Creates booking
The conflict: both transactions operate on the same room and overlapping dates, and both write.
Availability depends on dates. A room is not simply “available” or “booked” forever. Room 205 can hold several reservations as long as their date ranges do not overlap. An existing reservation conflicts with a new request when existing.check_in < new.check_out AND existing.check_out > new.check_in. For example, an existing 5–8 Oct booking does not conflict with 10–12 Oct.
Objective of this blog: to show how transaction management, concurrency control and row locking stop Room 205 from being sold twice.
Why double booking hurts: two guests hold confirmations for one room, so one is turned away, the hotel pays in compensation and lost trust, and the Booking table holds an invalid state.
THE REAL-WORLD FAILURE

“Both receive a confirmation email. Both arrive at the hotel. There is one room.”

This is a concurrency problem — not simply a normal application bug.
02 — Transaction

Think of a booking as one complete unit of work.

A transaction groups checking availability for the requested dates, creating the reservation and any related updates into an all-or-nothing operation.

COMMIT makes the changes permanent. ROLLBACK undoes changes made by the transaction if something goes wrong.

Opens the unit of work. Nothing is permanent yet.

COMMIT or ROLLBACK

COMMIT saves every step together; ROLLBACK undoes them all.

ACID, part 1. ACID is the reliability checklist for transactions. Two letters explain the all-or-nothing booking; Isolation and Durability come later.

A

C
Consistency

A committed transaction moves the database from one valid state to another, e.g. no overlapping reservations for a room.

04 — Schedules

Serial is safe. Concurrent is faster — but needs control.

A schedule describes the order in which operations from multiple transactions execute.

✓ Serial schedule

One transaction finishes before the next begins.

T1 → Check dates → Reserve → Commit
T2 → Check dates
T2 → Overlap found → Reject

⚠ Concurrent schedule (no control)

Operations are interleaved: both transactions read before either one writes.

T1 → Check dates → no overlap
T2 → Check dates → no overlap
T1 → INSERT booking
T2 → INSERT booking
T1, T2 → COMMIT → overlapping bookings
FeatureSerialConcurrent
ExecutionOne after anotherSimultaneous / interleaved
PerformanceLowerHigher
Conflict riskLowHigh without control

Same two requests, different order, different result

Order of operationsAaravMeeraDatabase state
Serial: T1 then T2BookedRejectedValid
Serial: T2 then T1RejectedBookedValid
Concurrent, no controlAcceptedAcceptedOverlapping bookings (invalid)

Both serial orders are correct; only the winner differs. The concurrent schedule fails because both CHECK steps run before either INSERT, so each transaction decides using out-of-date information.

05 — Serializability

Same result as some serial order, without interference.

Atomicity and Consistency were covered earlier. Here: why a concurrent schedule can still be correct, and the two remaining ACID properties.

Serializability is the key idea: a concurrent schedule is acceptable if its result is the same as some serial order of the same transactions (T1 then T2, or T2 then T1). In either order, only one of the two overlapping bookings can succeed. Concurrency control (such as locking) is what forces the DBMS to allow only such schedules.

ScheduleEquivalent to a serial order?Verdict
Unsafe interleavingNo: matches neither T1 → T2 nor T2 → T1Not serializable
Locked scheduleYes: same result as T1 then T2Serializable
I
Isolation

Concurrent transactions behave as if they did not interfere; the strength depends on the isolation level.

D
Durability

Committed bookings remain stored, even after a crash.

Isolation and double booking: Isolation is what failed in the unsafe schedule: T2 decided as if T1 did not exist. Durability then protects the winner: once COMMIT returns, Aarav’s booking survives a crash.
Simple connection: Isolation and concurrency control help protect Consistency, but they do not guarantee it alone. Consistency also depends on correct transaction logic and on rules such as constraints.

07 — The solution

Lock the room before changing it.

When a transaction intends to book Room 205, it can lock that room’s row with SELECT … FOR UPDATE. Another transaction requesting a lock on the same row waits until the first one commits or rolls back. This works as a gate only because every booking transaction follows the same steps, and because the date-overlap check is run after the lock is obtained.

T1 — Aarav

Lock Room 205 row
Check overlap for 10–12 Oct → none
INSERT booking
COMMIT → lock released

T2 — Meera

Requests same lock → WAIT
Lock granted after T1 commits
Recheck overlap → Aarav’s booking found
ROLLBACK / REJECT
Concurrency control

DBMS mechanisms that decide when a transaction may touch shared data, so concurrent runs stay serializable.

Row locking

A lock marks one row as in use. Others wanting a conflicting lock on that row must wait.

SELECT … FOR UPDATE

Reads the Room 205 row and locks it until COMMIT or ROLLBACK. T2’s same request waits, then continues.

Why wait? Waiting turns two overlapping attempts into a queue. T2 then re-checks and sees T1’s result.
08 — SQL implementation

From lock to commit: the SQL and the safe schedule.

The PostgreSQL implementation, read in order, followed by the safe run.

-- PostgreSQL, default READ COMMITTED isolation level
BEGIN;

-- 1. Lock the Room 205 row (other bookers of this room wait here)
SELECT room_no FROM Room
WHERE room_no = 205
FOR UPDATE;

-- 2. Check for overlapping reservations (runs after the lock is held)
SELECT COUNT(*) FROM Booking
WHERE room_no = 205
  AND check_in < DATE '2027-10-12'  -- existing check-in < new check-out
  AND check_out > DATE '2027-10-10';-- existing check-out > new check-in

-- 3a. Application logic: if the count is greater than 0 → ROLLBACK; reject the booking.
-- 3b. If the count is 0:
INSERT INTO Booking (customer, room_no, check_in, check_out)
VALUES ('Aarav', 205, DATE '2027-10-10', DATE '2027-10-12');

COMMIT;

The room itself is never marked “Booked”: availability is derived from the Booking table for the requested dates. FOR UPDATE locks the selected existing row, here the Room row, so it acts as a gate for that room. It does not lock “dates” in general, and locking the room row alone does not stop overlaps if some code path skips the lock. In PostgreSQL’s default READ COMMITTED level, each statement sees data committed before it starts, so T2’s overlap check, run after its wait, sees T1’s committed booking and rejects the request. Other isolation levels (or other DBMSs) have different locking and visibility rules.

B100 (5–8 Oct) shows that one room can hold several reservations when the date ranges do not overlap. A second line of defence can be a database-level safeguard. An ordinary UNIQUE constraint on room number alone would not work: it would allow only one booking per room ever, even for different dates. Preventing overlapping date ranges needs a range-aware constraint (for example, a PostgreSQL exclusion constraint using btree_gist with daterange), or locking and stronger isolation levels. The right mechanism depends on the database system and schema.

Takeaway

One room. Two requests. The database quietly decides the correct order.

Hotel booking looks simple from the user's screen, but behind that screen the DBMS must coordinate concurrent transactions. Transactions provide an all-or-nothing unit of work; ACID provides reliability; and concurrency control such as locking ensures that concurrent schedules behave like safe serial execution.
