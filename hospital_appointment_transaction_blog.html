When two patients click Book at the same time.

How transaction management prevents double-booking in a hospital appointment system using concurrency control, locking and serializability.

01 — THE PROBLEM

A simple booking can become a database problem.

Imagine a hospital where Dr. Sharma has one appointment slot available at 10:00 AM. At almost exactly the same moment, Patient A and Patient B open the appointment page and press Book.

“The slot was available when I checked.”
— Patient A and Patient B, simultaneously

This is a classic concurrency problem. Both requests are separate database transactions, but both are trying to change the same piece of data. Without proper transaction management, the hospital can end up with an inconsistent appointment schedule.

Reads the 10:00 AM slot and sees AVAILABLE.

02 — TRANSACTION BASICS

Think of a booking as one complete transaction.

A transaction is a logical unit of database work. For an appointment booking, it can be represented as a sequence of operations:

BEGIN→READ SLOT→CHECK→WRITE BOOKED→COMMIT

If something goes wrong before commit, the transaction can be rolled back. This keeps the appointment data from being left in an incorrect state.

A — Atomicity

Booking completes fully or is rolled back.

C — Consistency

The appointment schedule remains valid.

I — Isolation

Concurrent bookings do not corrupt each other.

D — Durability

A committed booking is preserved in a real database.

ACID is the set of properties that helps database transactions remain reliable.

03 — THE CONFLICT

Where exactly do the transactions conflict?

Let S represent the 10:00 AM appointment slot. Both transactions access the same data item.

Transaction T1 — Patient ATransaction T2 — Patient B
READ(S)READ(S)
CHECK: AVAILABLECHECK: AVAILABLE
WRITE(S = A)WRITE(S = B)
COMMITCOMMIT

The dangerous part is that both transactions write the same appointment record.

Read → Write

A transaction reads data that another transaction later changes.

Write → Read

One transaction changes data that another transaction reads.

Write → Write

Both transactions try to update the same slot. This is the key conflict in our example.

Possible result

The application may show two successful bookings for a slot that can only serve one patient.

04 — THE ANOMALY

Without control, “available” can be true twice.

Step 01

T1 reads

10:00 AM = AVAILABLE

Step 02

T2 reads

10:00 AM = AVAILABLE

Step 03

Both write

Two patients think they booked it.

Problem: the database has lost the guarantee that one appointment slot belongs to only one patient.

05 — SERIALIZABILITY

Make concurrent work behave like a safe serial order.

Serializability means that the final effect of concurrent transactions should be equivalent to some correct serial execution. For this case, a safe order is:

T1: Patient A books first→T2: Patient B checks after T1

Once T1 commits, T2 sees BOOKED and cannot assign the same slot to Patient B. The transactions may have arrived concurrently, but their conflicting operations are controlled in a serializable order.

Precedence graph

T1 → T2

No cycle: the graph gives the serial order T1 → T2, so the controlled schedule is conflict-serializable.

06 — THE SOLUTION

Lock the appointment before changing it.

An exclusive lock prevents another transaction from modifying the same appointment record while the first transaction is using it.

Transaction T1

Acquire X-Lock→Read→Write BOOKED→Commit→Release

Transaction T2

Try X-Lock→Wait→Read BOOKED→Reject

The important idea is not that T2 disappears. It waits until the conflicting operation is safely completed, then works with the latest value.

09 — WHY IT MATTERS

This pattern appears far beyond hospitals.

🚆 Railway booking

Two users cannot reserve the same seat.

🎟 Ticket booking

One ticket inventory item cannot be sold twice.

🏦 Banking

Concurrent balance updates must remain correct.

🛍 Online shopping

Limited-stock products need safe updates.

10 — TAKEAWAY

One slot. One winner. One consistent database.

Hospital appointment booking looks simple from the user's screen, but behind that screen the DBMS must coordinate concurrent transactions. By identifying conflicting operations, applying locks and maintaining a serializable execution order, transaction management prevents double-booking and keeps the appointment schedule consistent.

READ→LOCK→WRITE→COMMIT→RELEASE
