Transaction Management in a Cab Booking System

Discover how database transactions prevent duplicate driver assignments and maintain consistency when many passengers book rides simultaneously.

Concurrency · COMMIT · ROLLBACK · ACID

01 · INTRODUCTION

Why Transaction Management Matters

Imagine a busy evening when many people are leaving their colleges and offices at the same time. Hundreds of users open a cab-booking application and request rides.

Suppose only one driver, Driver D101, is available nearby. Two users, Pooja and Riya, request a cab almost at the same time.

If the system does not properly manage these requests, both users might receive the same driver. Two rides would be confirmed even though only one driver is available.

Key concept: Transaction management ensures that concurrent ride requests are processed safely and that the database remains consistent.

03 · CONCURRENCY PROBLEM

When Two Users Request the Same Driver

  • Driver D101 is available.
  • Pooja requests a ride.
  • Riya requests a ride at almost the same time.
  • Both requests identify D101 as available.
Driver D101 — Available
↓
Pooja's Request (T1)
↓
Reads Available
↓
Assigns D101
Riya's Request (T2)
↓
Reads Available
↓
Assigns D101
↓
CONFLICT: One driver, two ride assignments!

This is called a concurrency problem. Both transactions may read the same old status before either transaction updates the driver record.

04 · TRANSACTION SOLUTION

How Transaction Management Solves the Problem

A transaction treats a group of database operations as one logical unit. If an operation fails, the system can roll back the incomplete changes.

BEGIN TRANSACTION
↓
Find an Available Driver
↓
Reserve the Driver Safely
↓
Create the Ride Record
↓
Update Driver Status
↓
COMMIT — Save Changes

Example: Pooja's Transaction

T1: Pooja Requests a Ride
↓
Reserve Driver D101
↓
Create Ride R501
↓
Set D101 = Assigned
↓
COMMIT

When Riya's transaction tries to reserve D101, the conditional update will fail because the driver is no longer available. The system can search for another driver or inform Riya that no suitable driver is available.

ROLLBACK: If ride creation fails after reserving the driver, the system should undo the reservation so the driver does not remain incorrectly marked as assigned.
05 · SQL IMPLEMENTATION

Transaction SQL Example

The condition WHERE Driver_ID = 'D101' AND Status = 'Available' allows the update only when the driver is still available.

Transaction T1 — Pooja

START TRANSACTION;

UPDATE DRIVER
SET Status = 'Assigned'
WHERE Driver_ID = 'D101'
  AND Status = 'Available';

-- Application must check affected rows.
-- Continue only if exactly one row was updated.

INSERT INTO RIDE
    (Ride_ID, User_ID, Driver_ID, Status)
VALUES
    ('R501', 'U101', 'D101', 'Confirmed');

COMMIT;

Transaction T2 — Riya

START TRANSACTION;

UPDATE DRIVER
SET Status = 'Assigned'
WHERE Driver_ID = 'D101'
  AND Status = 'Available';

-- If zero rows are affected:
-- ROLLBACK and search for another driver.

INSERT INTO RIDE
    (Ride_ID, User_ID, Driver_ID, Status)
VALUES
    ('R502', 'U102', 'D101', 'Confirmed');

COMMIT;
Important: These are illustrative SQL examples. A real application must check the number of rows updated before inserting the ride. If zero rows were updated, it must not confirm a ride using that driver. The application should roll back and try another driver. Proper database isolation, locking, and constraints add further protection.
06 · ACID PROPERTIES

ACID Properties in a Cab Booking System

1. Atomicity

Either the driver assignment and ride creation succeed together, or incomplete changes are rolled back.

2. Consistency

Database rules remain valid. A driver should not be assigned to two active rides.

3. Isolation

Concurrent requests are controlled so that they do not incorrectly interfere with one another.

4. Durability

After a successful commit, the saved ride remains recorded even if the application restarts.

07 · CONCLUSION

Conclusion

Transaction management is essential in a cab-booking system because many users may request rides at the same time.

Using transactions, conditional updates, appropriate locking, and rollback handling helps prevent duplicate driver assignments and keeps the database reliable.

Remember: A ride should be confirmed only after the driver has been successfully reserved.
