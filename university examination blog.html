Transaction Management in a University Examination System

Discover how transactions, locks and ACID properties prevent lost updates and keep every student's result accurate when many people work on the same marks.

01 · INTRODUCTION

Why Transaction Management Matters

A university database is used by examiners, students and revaluation staff. When two people update the same marks at the same time, one update may be lost.

Transaction management and concurrency control help keep results accurate even when many users access the database together.

Key concept: Transaction management ensures that concurrent updates to marks are processed safely and that the database remains consistent.
02 · CONCURRENCY PROBLEM

Example: The Lost Update Problem

Suppose Roll No. 1 has 62 marks in DBMS.

Transaction Who Action
T1 Examiner Changes 62 to 68
T2 Revaluation officer Adds 3 marks
Roll No. 1 — DBMS Marks = 62
↓
T1 — Examiner
↓
Reads 62
↓
Saves 68
T2 — Revaluation
↓
Reads 62
↓
Saves 65
↓
LOST UPDATE: The examiner's correction disappears!

If both read 62 at the same time, T1 saves 68 and T2 may save 65. The examiner's correction is lost. The correct result is 71 if the operations happen in order:

62 → 68 → 71
03 · TRANSACTION

What Is a Transaction?

A transaction is a group of database operations treated as one unit. In an exam system, it can read marks, update marks, recalculate the total and grade, and then commit the changes.

BEGIN TRANSACTION
↓
Read Marks
↓
Update Marks
↓
Recalculate Total and Grade
↓
COMMIT — Save Changes
04 · CONCURRENCY CONTROL

Concurrency Control and Locks

A serial schedule completes one transaction before starting the next. A concurrent schedule lets transactions overlap, improving efficiency, but the DBMS must control access to avoid errors.

Shared Lock

Allows multiple users to read data, such as students viewing results.

Exclusive Lock

Allows one transaction to update data, such as an examiner changing marks.

Example: Locking Fixes the Lost Update

Marks = 62
↓
T1 locks the record, updates 62 → 68
↓
T1 COMMITS and releases the lock
↓
T2 reads 68 and adds 3
↓
T2 saves 71 — Neither update is lost
START TRANSACTION;

SELECT Marks FROM RESULT
WHERE Roll_No = 1 AND Subject = 'DBMS'
FOR UPDATE;   -- exclusive lock

UPDATE RESULT
SET Marks = Marks + 3
WHERE Roll_No = 1 AND Subject = 'DBMS';

COMMIT;
Note: This is an illustrative SQL example. Exact locking syntax and behaviour vary between database systems.
05 · ACID PROPERTIES

ACID Properties in an Examination System

1. Atomicity

All operations happen, or none happen.

2. Consistency

Marks, totals and grades remain valid.

3. Isolation

Transactions do not interfere incorrectly.

4. Durability

Committed changes remain saved, even after a crash.

06 · COMMIT, ROLLBACK AND SERIALIZABILITY

Saving, Undoing and Staying Correct

COMMIT

Saves changes permanently.

ROLLBACK

Cancels incomplete changes.

ROLLBACK example: If a grace-marks update fails halfway, rollback prevents only some students from receiving the update.

Serializability

Serializability means concurrent transactions produce the same correct result as a safe serial order.

07 · USES AND CONCLUSION

Conclusion

These concepts help with:

Marks Entry Revaluation Hall-Ticket Generation Exam Registration Fee Payments Result Publication

In conclusion, transaction management, ACID properties and locks help a university database handle many users while keeping every student's result correct.

Remember: Concurrent updates must never overwrite one another. Lock, update, commit, and only then let the next transaction proceed.
